## 0. Процесс работы ИИ над кодом

1. **Сначала план, потом код.** Перед заметной задачей: 3–7 строк — какие файлы/классы затронешь, как они связаны. Для мелких правок — сразу код.
2. **Маленькие шаги.** Одна задача — один логический кусок, который можно запустить и проверить. Не переписывай пол-проекта за раз.
3. **Только Godot 4 синтаксис.** Самая частая ошибка ИИ — код из Godot 3 (см. раздел 9). Не уверен в API — скажи об этом и предложи проверить в документации, не выдумывай методы.
4. **Не плодить мёртвый код.** Никаких закомментированных кусков «на всякий случай», неиспользуемых переменных, TODO без причины.
5. **Не оптимизировать заранее,** но и не писать заведомо медленно (раздел 6).
6. **Объясняй новичку.** Автор учится: после кода — коротко, что сделано и почему так. Неочевидные решения — комментарий в коде.
7. **Логика игры — с тестами** (раздел 8). Визуал — без тестов, проверка запуском.
8. **В конце задачи пройди чек-лист** (раздел 11).

## 1. Архитектура (главное для нашей игры)

### 1.1. Симуляция отдельно от отображения
Игра — PvP с будущим мультиплеером на детерминированной симуляции. Поэтому код делится на два слоя:

| Слой | Что | На чём | Знает о другом слое? |
|---|---|---|---|
| **Симуляция (sim)** | Правила: мобы, башни, урон, экономика, раунды, осада | Классы `RefCounted` / `Resource`, **без нод и сцен** | **Нет.** Ничего не знает о графике, звуке, UI |
| **Отображение (view)** | Спрайты, анимации, UI, звук, ввод | Ноды и сцены Godot | Да: читает состояние sim, подписывается на её сигналы, передаёт ввод игрока командами |

Зачем: симуляцию можно тестировать без запуска сцены, гонять на сервере, проигрывать реплеи и прогонять ботов быстрее реального времени.

**Ввод игрока → команда.** Любое действие игрока (купить башню, поставить, отправить мобов) — это объект-команда (`PlaceTowerCommand` и т.п.), который передаётся в симуляцию. Симуляция меняется только через команды и тики. Это база для сети и реплеев.

### 1.2. Детерминизм симуляции
Одинаковые начальные данные + одинаковые команды → **бит-в-бит одинаковый результат** на любом компьютере.
- Фиксированный тик симуляции (ориентир: 20 тиков/сек), **не** зависим от `delta` и FPS. Отображение интерполирует между тиками.
- **Только целые числа в симуляции**: HP, урон, золото, координаты (позиция моба — прогресс по пути в целых единицах, например 1/1000 клетки). Float на разных машинах может считаться по-разному.
- Случайность — только через `RandomNumberGenerator` симуляции с сидом матча. **Запрещено** в sim: `randi()`, `randf()`, `randomize()`, `Time`, `OS`, физический движок Godot.
- Порядок обработки детерминирован: массивы, сортировка по стабильному ключу (id).

### 1.3. Данные вместо кода
- Башни, мобы, герои, волны описываются **кастомными ресурсами** (`TowerData extends Resource`, файлы `.tres` в `res://data/`).
- В коде **нет** захардкоженных статов. Новая башня = новый `.tres`, а не новый скрипт (скрипт только для действительно уникального поведения).
- Синергии и контры — через **теги** (`StringName` или enum-флаги): `&"fire"`, `&"flying"`, `&"armored"`.

### 1.4. Связь между частями
- **«Signal up, call down»**: родитель вызывает методы детей; дети сообщают наверх сигналами и не знают о родителе.
- Соседние ноды не держат жёстких ссылок друг на друга — общается их общий родитель.
- **Шина событий (autoload `EventBus`)** — только для действительно глобальных событий (матч начался/закончился, игрок выбыл). Не тащить туда всё подряд.
- **Autoload-ов минимум.** Каждый новый autoload — запись в `decisions.md` с причиной.
- Зависимости передаём явно: метод `setup(...)` / аргументы конструктора, а не поиск по дереву (`get_node("../../..")`) и не глобальные переменные.

### 1.5. Композиция вместо наследования
- Иерархии наследования не глубже 2–3 уровней.
- Поведение собираем из компонентов/данных (башня = данные + набор эффектов), а не через `FireTowerWithSlowAndAura extends FireTower extends Tower`.

### 1.6. Структура проекта
```
res://
├── src/
│   ├── sim/          # симуляция: чистая логика, без нод
│   │   ├── commands/
│   │   ├── data/     # классы ресурсов: TowerData, MobData, HeroData…
│   │   └── …
│   ├── view/         # ноды и сцены отображения
│   ├── ui/
│   └── autoload/
├── data/             # .tres с конкретными башнями, мобами, героями, волнами
│   ├── towers/
│   ├── mobs/
│   └── heroes/
├── scenes/           # сцены верхнего уровня (меню, матч)
├── assets/           # графика, звук, шрифты
├── tests/            # тесты GUT
└── addons/           # сторонние плагины (GUT и т.д.)
```

## 2. Стиль кода (по официальному style guide Godot)

### 2.1. Именование
| Что | Стиль | Пример |
|---|---|---|
| Файлы и папки | `snake_case` | `tower_data.gd`, `mob_spawner.tscn` |
| Классы, `class_name`, ноды | `PascalCase` | `TowerData`, `MobSpawner` |
| Переменные, функции | `snake_case` | `gold_amount`, `get_income()` |
| Приватные члены | `_snake_case` | `_tick_count`, `_recalculate()` |
| Константы, значения enum | `CONSTANT_CASE` | `MAX_PLAYERS`, `State.IDLE` |
| Enum (тип) | `PascalCase` | `enum DamageType { PHYSICAL, MAGIC }` |
| Сигналы | прошедшее время | `mob_killed`, `round_started`, `gold_changed` |
| Булевы | префикс `is_/has_/can_` | `is_alive`, `can_afford` |
| Обработчики сигналов | `_on_<источник>_<сигнал>` | `_on_shop_item_bought` |

Имена — полные и говорящие: `damage_per_tick`, а не `dpt`; `target_mob`, а не `t`.

### 2.2. Порядок внутри скрипта
```
@tool                     # если нужно
class_name ИмяКласса
extends Базовый
## Докстринг: что делает класс (1–3 строки).

signals
enums
constants
@export переменные
публичные переменные
приватные переменные (_)
@onready переменные

_init()
_ready()
остальные встроенные (_process, _input…)
публичные методы
приватные методы
внутренние классы
```

### 2.3. Форматирование
- Отступ — табы (по умолчанию в Godot). Строка ≤ 100 символов.
- Две пустые строки между функциями.
- `and`/`or`/`not`, а не `&&`/`||`/`!`.
- Продолжение длинной строки — двойной отступ (кроме массивов/словарей/enum — одинарный).
- Комментарии `#` объясняют **почему**, а не что. Докстринги `##` — у каждого класса и публичного метода.

### 2.4. Статическая типизация — везде, без исключений
```gdscript
var gold: int = 0
var towers: Array[Tower] = []
var stats_by_id: Dictionary[StringName, TowerData] = {}
const MAX_LEVEL: int = 3

func deal_damage(target: Mob, amount: int) -> void:
	...

func get_income() -> int:
	return _base_income + _send_bonus
```
- Типы у всех переменных, параметров, возвращаемых значений (`-> void` тоже).
- Типизированные массивы и словари.
- Приведение типов: `as` + проверка на `null`, или `is` перед использованием.
- Типизированный код быстрее и ловит ошибки в редакторе до запуска.

### 2.5. Настройки проекта (включить при создании проекта)
Project Settings → Debug → GDScript (включить Advanced Settings). Поставить **Error** для:
`untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_cast`, `unsafe_call_argument`, `unused_variable`, `unused_parameter`, `shadowed_variable`, `return_value_discarded` (последнее — Warning).
Предупреждение игнорируется только через `@warning_ignore("имя")` **с комментарием почему**.

## 3. Принципы хорошего кода (прагматичный ООП/SOLID)

- **Одна ответственность.** Класс делает одно дело. `Economy` считает золото, `Shop` — витрину, `WaveSpawner` — спавн. Никаких `GameManager` на 2000 строк.
- **Короткие функции.** Ориентир — до 30 строк. Длиннее — разбить.
- **Без магических чисел.** Числа — в константы или `.tres`-данные.
- **Ранний выход** вместо глубокой вложенности: `if not can_afford: return`.
- **Не дублировать.** Повторилось третий раз — выносим в функцию/класс.
- **Явное лучше неявного.** Никаких сеттеров с неожиданными побочными эффектами без докстринга.
- **Инкапсуляция.** Внешний код меняет состояние через методы (`economy.spend(10)`), а не напрямую (`economy._gold -= 10`).
- **Простота важнее «правильных» паттернов.** Паттерн вводим, когда он решает реальную проблему, а не «на будущее» (YAGNI).
- Полезные паттерны для нас: **Command** (ввод игрока), **State machine** (фазы раунда), **Data-driven / Type Object** (ресурсы башен и мобов), **Observer** (сигналы).

## 4. Ноды и сцены (слой view)

- Ссылки на дочерние ноды — через `@onready var x: Type = $Path` или `%UniqueName` (уникальные имена для важных нод). Без длинных хрупких путей.
- Сцена самодостаточна: не полагается на то, что лежит у родителя. Всё нужное — через `@export` или `setup()`.
- Подключение сигналов в коде: `button.pressed.connect(_on_button_pressed)` (не строками).
- Отключай обработку, когда она не нужна: `set_process(false)`.
- Нода, которая больше не нужна — `queue_free()`, не `free()`.

## 5. Ошибки и отладка

- `assert(условие, "сообщение")` — для инвариантов («у моба не может быть HP < 0»). Срабатывает только в отладке.
- `push_error()` / `push_warning()` — для ошибок во время работы. Не `print()`.
- `print()` — только временно при отладке, не коммитить.
- Не глотать ошибки молча: если функция может не сработать — вернуть результат/`bool` и обработать.

## 6. Производительность

Цель: стабильные 60 FPS при сотнях мобов на поле.

**Всегда:**
- Статическая типизация (раздел 2.4).
- Ноды кэшировать (`@onready`), **никогда** `get_node()`/`$` внутри `_process`/`_physics_process`/циклов.
- **Один центральный цикл** в симуляции обрабатывает массив мобов. **Не** 300 нод, у каждой свой `_process`.
- Поиск целей для башен — по данным симуляции (прогресс мобов по пути), а не физическими `Area2D` и коллизиями.
- В горячих циклах не создавать лишних объектов, массивов, строк; не использовать `Dictionary` там, где хватит массива или полей класса.
- `StringName` (`&"fire"`) для тегов и ключей, а не `String`.

**Только когда профайлер покажет проблему:**
- Пулинг объектов — в GDScript для простых объектов обычно не нужен (нет сборщика мусора); пулить только тяжёлые сцены с дорогой инициализацией.
- `MultiMeshInstance2D` / `RenderingServer` напрямую — если мобов/снарядов тысячи.
- Перенос горячего кода в GDExtension (C++) — крайняя мера.

**Измерять, а не гадать:** встроенный Profiler и Monitors (Debugger → Profiler / Monitors). Оптимизация без замера — запрещена.

## 7. Сеть (на будущее, но учитываем сейчас)
- Передаём по сети только **команды игроков** и номер тика, не состояние мира.
- Сервер (или хост) — источник истины; клиенты не могут «нарисовать» себе золото.
- Проверка рассинхрона: хэш состояния симуляции каждые N тиков.
- Поэтому раздел 1.2 (детерминизм) — не опционален.

## 8. Тесты
- Фреймворк: **GUT 9.x** (для Godot 4.7 — ветка `godot_4_7`), папка `res://tests/`.
- Обязательно тестируем симуляцию: экономику, урон и контры, формирование пар и осады, конец матча.
- **Тест детерминизма:** один сид + один список команд, прогнать дважды → одинаковый хэш состояния.
- Баг в логике → сначала тест, который его воспроизводит, потом исправление.
- Имена: `test_<что>_<условие>_<ожидание>()`, например `test_spend_gold_when_not_enough_returns_false()`.

## 9. Ловушки: Godot 3 vs Godot 4 (ИИ часто путает)

| ❌ Godot 3 (не писать) | ✅ Godot 4 |
|---|---|
| `export var x = 1` | `@export var x: int = 1` |
| `onready var n = $N` | `@onready var n: Node2D = $N` |
| `tool` | `@tool` |
| `yield(obj, "signal")` | `await obj.signal` |
| `connect("pressed", self, "_on_p")` | `pressed.connect(_on_p)` |
| `emit_signal("died")` | `died.emit()` |
| `setget set_x, get_x` | `var x: int: set = set_x, get = get_x` |
| `KinematicBody2D` | `CharacterBody2D` |
| `instance()` | `instantiate()` |
| `deg2rad()` | `deg_to_rad()` |
| `PoolStringArray` | `PackedStringArray` |
| `OS.get_ticks_msec()` | `Time.get_ticks_msec()` |

## 12. Шаблон скрипта
```gdscript
class_name Economy
extends RefCounted
## Золото и доход одного игрока. Часть симуляции: без нод, только целые числа.

signal gold_changed(new_amount: int)

const START_GOLD: int = 100

var gold: int = START_GOLD

var _income: int = 0


func can_afford(cost: int) -> bool:
	return gold >= cost


## Списывает золото. Возвращает false, если не хватает.
func spend(cost: int) -> bool:
	assert(cost >= 0, "Стоимость не может быть отрицательной")
	if not can_afford(cost):
		return false
	gold -= cost
	gold_changed.emit(gold)
	return true


func add_income(amount: int) -> void:
	_income += amount


func apply_round_income() -> void:
	gold += _income
	gold_changed.emit(gold)
```
